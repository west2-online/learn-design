# task1

> [!TIP]
> 在小半年的学习后，你已经有了基础的设计、审美与协作能力。
>
> 接下来我们并不希望你急着学习所有软件，也无需仅靠选择的方向决定人生。
>
> 我们仅希望你专注一件事：产品。设计无法脱离实现，而产品导向是设计实现中最现实的理由。
>
> 理念中的美要投射到现实，要真的作为人不可或缺的一部分存在，就必须强迫自己不在非艺术创作导向的设计中投入过多的自我感动。

## 学习

### 产品的基本要求

这里主要讨论软件与互联网产品。调研产品相关的岗位 JD 时，你会看到需求分析、数据分析、PRD、项目推进等要求，但仅记住这些名词，很难知道自己到底应该学到什么程度。

或许，你可以先围绕三个问题理解产品工作：为谁解决什么问题？为什么这样做值得？怎样让方案落地并证明它产生了价值？

#### 先了解岗位之间的分工

- 产品经理 / 产品助理
  - 侧重问题定义、产品目标、需求取舍、方案规则与跨团队推进，持续跟进实际效果。
  - 助理或实习生通常先在明确范围内完成调研、需求整理、原型、验收或数据跟踪，再逐步承担完整模块。
- 用户研究员
  - 侧重研究问题、样本招募、访谈 / 观察 / 测试、证据分析，帮助团队理解用户与验证假设。
- 产品设计师 / UI \& UX 设计师
  - 侧重信息架构、操作流程、交互与视觉表达、可用性验证和设计交付，也需要参与前期问题定义。
- 产品运营
  - 侧重产品如何被用户发现、开始使用和持续使用，通过内容、活动、用户服务及数据反馈推动改进。
- 项目经理 / 交付负责人
  - 侧重进度、资源、依赖与风险，帮助团队按约定完成交付。

这些是常见侧重，实际职责会随团队而变化，小团队中也可能由同一人兼任。产品经理需要推动共同决策，但不代表能代替设计、研发、测试等岗位作所有专业判断。可以结合 [Atlassian 对产品经理职责的说明](https://www.atlassian.com/agile/product-management/product-manager)理解这种协作关系。

#### 按生命周期理解技能要求

> [!NOTE]
> 项目通常有明确的范围与交付节点；产品可能经历多个项目和版本，在上线后继续运营多年。
>
> 从发现问题开始，产品就已进入生命周期。下面按工作重心分阶段，方便你建立全貌。
>
> 但在实际工作中，调研、设计、开发和验证会反复交叉，并没有人等到你把所有文档写完才开始下一步。

1. 项目之前：发现问题与判断机会
    - 用户研究与需求分析
        - 找到目标用户、使用场景、想完成的任务和当前障碍，区分用户的原话、自己的解释与待验证的假设。
        - 学习访谈、观察、问卷等方法的适用条件；能根据问题选择方法，避免用引导性提问替自己的想法找支持。
    - 市场、业务与竞品分析
        - 理解行业、服务对象、使用者与付费 / 决策者，了解产品依靠什么持续提供服务。
        - 比较同一任务的不同解决办法，包括竞品、表格、人工和线下流程；说明现有方案为什么不够，而非只收集界面截图。
    - 数据分析与可行性判断
        - 从已有记录中检查问题的频率、影响范围和严重程度，说明数据来源及局限。
        - 与设计、研发、运营等共同判断技术条件、资源、时间和维护成本，允许得出暂缓或不做的结论。
    - 典型产出：问题定义、研究记录、竞品 / 替代方案分析、关键假设与立项建议。
2. 项目伊始：确定目标与需求范围
    - 产品目标与成功指标
        - 把“提升体验”具体化为某类用户在某个任务上的改善，例如减少报名失败或缩短审核耗时。
        - 明确指标的定义、数据来源、统计周期、现状与目标；同时关注不能恶化的指标，例如减少步骤时不能增加误操作。
    - 需求管理与优先级
        - 建立需求池，记录来源、用户问题、价值、依赖、成本和不确定性；区分必须做、可以后做与不做。
        - 了解 RICE（覆盖人数、影响、信心与投入）等排序方法，但要能解释依据，不把主观打分当成客观结论。
    - 最小可行产品（MVP）与路线图（Roadmap）
        - 找到能验证核心价值的最小完整方案，明确本版做什么、暂不做什么，以及下一步取决于什么证据。
        - 路线图表达阶段目标和演进方向；具体排期需与实际承担工作的人共同评估。
    - 典型产出：产品简报（Brief）、指标定义、需求优先级、版本范围与初步路线图。
3. 方案形成：把需求变成可讨论、可实现的规则
    - 产品需求文档（PRD）
        - 写清背景、目标、用户与场景、范围、流程、业务规则、验收标准和待确认问题。
        - 例如“支持报名”还需说明谁能报名、何时截止、名额已满怎么办、能否取消、重复提交怎样处理。
        - 文档随决策更新，重点是让团队形成一致理解；可参考 [Atlassian 的 PRD 指南](https://www.atlassian.com/agile/product-management/requirements)。
    - 业务流程、信息架构与原型 / 交互设计
        - 能用流程图、页面结构和可点击原型表达任务路径，覆盖成功、加载、空、错误、权限不足和中断恢复等相关状态。
        - 分清业务规则与界面表达，和设计师共同检查文案、反馈、可访问性与操作成本。
    - 方案验证与技术沟通
        - 在投入完整开发前，用草图、原型或小范围试用检验关键假设，记录用户实际怎样操作。
        - 理解前后端、接口、数据字段、权限与第三方服务的基本关系，能与研发讨论依赖和限制；具体技术方案由相应专业人员评估。
    - 典型产出：PRD、流程图、原型、验证记录与评审后的方案决定。
4. 项目推进：协作开发与处理变化
    - 跨职能沟通与需求评审
        - 和设计、研发、测试、运营等对齐目标、规则和验收口径，明确负责人、依赖及待解决问题。
        - 会写结论清晰的会议纪要，记录决定、行动项、责任人与时间；能处理分歧，推动问题得到解决。
    - 迭代与进度管理
        - 了解敏捷迭代和任务看板，能跟踪里程碑、阻塞、风险与交付状态。
        - 遇到延期时，与团队讨论缩小范围、调整方案或排期，并说明对用户和业务的影响。
    - 变更管理与实现走查
        - 新需求进入时评估收益、成本和对既有流程的影响，同步文档、设计与验收标准。
        - 在开发过程中检查实际实现，及时澄清遗漏的规则；区分缺陷、需求变更与体验优化。
    - 典型产出：迭代计划、任务看板、评审 / 决策记录、变更记录与问题清单。
5. 上线前后：验收、发布与使用准备
    - 业务验收与质量协作
        - 按需求逐项检查核心流程、边界和异常情况，记录复现步骤、影响与处理结果。
        - 产品侧确认业务目标和规则是否满足；研发、测试等负责各自的技术质量检查，并共同判断是否具备上线条件。
    - 指标采集与埋点验收
        - 在开发前约定要记录的事件、触发时机、字段和统计口径，上线前检查数据是否漏报或重复。
        - 理解“埋点”是记录用户行为或系统事件；只有页面上线，没有可靠的数据，也无法判断效果。
    - 发布与运营准备
        - 与团队确定发布范围、试运行 / 灰度安排、观察指标，以及出现什么问题时暂停或回滚。
        - 准备更新说明、使用指引、反馈入口和必要培训，明确上线后的支持责任人。
    - 典型产出：验收记录、发布检查清单、指标 / 埋点说明、使用指引与应急安排。
6. 上线之后：验证效果与持续迭代
    - 用户反馈与问题定位
        - 汇总访谈、客服、反馈入口和行为数据，区分个别意见、普遍问题与不同用户群的差异。
        - 将问题追溯到具体流程和规则，再决定修复、优化、继续观察或补做研究。
    - 数据分析与实验
        - 学习表格统计、数据清洗和图表表达，按岗位需要进一步掌握 SQL 查询、关联与聚合；Python、BI 等按实际需求深入。
        - 理解漏斗（各步骤的流失）、留存（用户是否回来）与用户分组，避免只看下载量、浏览量等表面数字。
        - 了解 A/B 测试的对照思路、样本与周期要求；小项目先做好任务测试和持续观察，不用少量样本或简单前后对比宣称因果。
    - 复盘与版本决策
        - 对照最初目标说明哪些假设得到支持、哪些被推翻，决定继续投入、修改方向或停止功能。
        - 需求池和路线图随证据更新；用户研究、竞品分析与业务判断在这里仍会继续。
    - 典型产出：效果分析、反馈分类、实验 / 验证报告、复盘与下一版计划。
7. 长期维护与退出：让产品能够持续服务，也能够妥善结束
    - 维护与交接
        - 关注服务成本、稳定性、旧版本兼容、规则变化与长期未解决的问题，平衡新功能和维护投入。
        - 保留可用的文档、版本记录与责任分工，让后续成员能够接手。
    - 功能下线与产品退出
        - 根据使用情况、价值、成本和替代方案评估是否停止投入。
        - 与相关岗位安排通知、替代路径、数据迁移 / 导出和后续支持，验证仍在使用产品的人能否顺利过渡。
    - 典型产出：维护计划、交接说明、下线 / 迁移方案与结果记录。

例如做一个“社团活动报名”产品，你需要先弄清报名者和组织者遇到的具体问题，再决定本版是否只解决报名、名额与取消；与设计、研发讨论满员、重复报名等规则，验收并上线后检查失败原因和审核耗时，最后考虑下一届负责人如何接手。这个过程中的研究、取舍、表达、协作和验证，就是这些岗位能力的实际用途。

#### 贯穿各阶段的思维与能力

- 用户意识与同理心
  - 从真实场景理解需求，主动接触与自己经验不同的用户，留意少数人和容易被忽略的使用障碍。
- 逻辑思维与系统思维
  - 拆清概念、条件、流程、因果与例外；修改一个规则时，能追问它影响哪些角色、页面、数据和后续环节。
- 商业与价值意识
  - 同时考虑用户收益、组织目标和持续服务的成本。商业产品需要理解付费与收入，校园 / 公益项目也需要考虑资源和维护，不能只问功能是否有趣。
- 证据意识与批判性思维
  - 区分事实、假设与观点；会检查数据口径、样本偏差和反例，能根据新证据修改原来的判断。
- 优先级与取舍能力
  - 在有限时间和资源下解释为什么先做这件事、放弃了什么，以及什么情况下应重新考虑。
- 沟通、协商与责任意识
  - 面向不同岗位清楚表达问题和约束，推动决定落地，跟进上线后的结果。
  - 涉及隐私、授权、误导或滥用风险时，能识别问题并及时与相应负责人确认处理方式。

你还可以结合 [GOV.UK 的服务交付阶段指南](https://www.gov.uk/service-manual/agile-delivery)，按 Discovery、Alpha、Beta、Live、Retirement 查看从探索到退出的工作。它以公共服务为背景，可以帮助理解生命周期，但商业目标与具体分工仍需结合自己的产品判断。

### 产品导向的思考

就事实而言，以上仅仅是一种泛泛的概念性讲述，甚至可能对你的独立思考起到反作用。我们真正意在让你们体会的并不是上面这些套话，而是形成自己的产品思考流程。

或许，我们可以尝试从对世界上曾存在过的一个 old good thing -- 苹果公司的演进历程引入思考，尤其是从乔布斯本人的思想转变中摸到一丝产品哲学的精髓。这里说的“产品哲学”你可以这样理解：**你相信什么样的生活值得追求，怎样把这种相信变成别人用得上的东西，以及愿意为此承担哪些代价。** 这样它就会落在价格、按钮、兼容性、服务规则和商业模式的边界里，不会太过天马行空而让人摸不着头脑。

> [!NOTE]
> 下面的梳理是我们尝试结合公开言论与妄自揣测的产品决策作出的解读。
>
> 其实一个人的内心并无法由几场发布会完整还原，一家公司的成果也来自许多人的共同工作。
>
> 面对下面的分析，我们应该做到的是：练习思考与判断，保留质疑苹果、质疑乔布斯、质疑这篇文章的能力与动力。

#### 产品仅是技术/物品/服务吗？

假设你回到 2001 年，准备做一台音乐播放器。你可能会先列出硬盘容量、重量、续航、音质，再研究怎样把外壳做得漂亮。这些工作当然有用，但它们还没有回答一个问题：一个喜欢听歌的人，为什么要把自己的日常生活交给你设计的这套东西？

当年的 iPod 配备 5GB 硬盘，苹果以最多容纳约 1,000 首歌曲介绍它，同时提供与 Mac 上 iTunes 自动同步的功能。请留意其中的两个尺度：5GB 描述机器能存多少数据，“把自己的音乐带在身边”描述人能过怎样的生活。容量需要与体积、选歌方式、传输和管理一起成立，才会成为后者。（详见 [苹果 2001 年的 iPod 发布资料](https://www.apple.com/newsroom/2001/10/23Apple-Presents-iPod/)）

你可以想象：如果装歌要折腾一晚上，出门前不知道有没有同步成功，想听的歌又很难找到，那么再大的硬盘也未必让听歌更自在。反过来，一个滚轮本身没有神奇之处，它的意义在于让手指能从大量歌曲中找到想听的那一首。用户在产品身上关心的，是这些环节共同构成的经历。

2003 年 4 月，苹果又在美国面向 Mac 用户推出 [iTunes Music Store](https://www.apple.com/newsroom/2003/04/28Apple-Launches-the-iTunes-Music-Store/)，提供每首 0.99 美元、无需订阅的购歌方式，将购买、下载、管理和播放放进同一个应用。这一步把唱片公司的授权、消费者的支付和使用规则也纳入了体验。

因此，iPod 的产品边界很难只画在机身周围。用户实际接触的是一组**关系**：音乐从哪里来，谁有权提供它，我怎样付款，怎样带走，换设备后还能否继续使用。设备、软件、内容和规则共同决定了这段经历。只复制外壳和滚轮，无法复制这组关系。

**为什么这可以叫作哲学？因为每一种安排都在回答“什么更值得”。** 让人自行管理每一个文件，可以增加控制权，也会要求人承担更多学习与维护；让软件自动处理，可以减少操作，也可能使规则变得不透明。技术帮助我们实现选择，却不能单凭自身决定哪一种生活更好。我们还需要讨论服务的是谁、哪些自由值得保留、便利的代价是否能够接受。

“简单”因而也需要继续追问：对谁简单？是把复杂性留给团队处理，还是把高度自定义向客户开放？是用户理解了系统，还是用户暂时看不见系统的限制？如果一个设计只在购买时显得轻松，却让维修、迁移和退出异常困难，那么它的简单是否意味着仅仅是一个需要被说明的边界被设计者精心的隔离掉了呢？

回到设计本身，字体、材质、动画和留白当然重要。它们让价值能够被感知：一段清楚的错误说明可以减少人的无助，一个诚实的价格页面可以减少猜疑。但我们以产品的视角思考时，就必须尝试解释这些形式与人的处境有什么关系，以及检查实际使用是否兑现了它们的承诺。

> [!TIP]
> 你可以先试着问：如果去掉品牌标志，这个产品仍然为人保留了什么？如果只留下广告里的价值主张，实际使用又兑现了多少？
>
> 品牌带来的认同、归属和愉悦当然是体验的一部分，但“我喜欢它可能让我成为的那种人”与“它确实帮助了我”之间的鸿沟，恰恰是消费主义与实用主义之间的碰撞。

#### 产品仅是一种模式或一套循环吗？

> [!NOTE]
> Be water, my friend.

我们可以很容易的把前面的内容整理成一套流程：发现需求，定义问题，制作原型，验证，迭代。很遗憾的是，流程可以帮助我们少遗漏需要考虑的事情，但其本身无法替我们决定目标是否值得追求。而乔布斯、库克或苹果的经历值得思考，恰恰在于这些行为主体既有久持不辍的信念，也决然做出过与自己先前选择截然不同的决定。把这些变化压缩成“极简”、“闭环”或“用户不知道自己要什么”，会丢掉最需要思考的那一丝韵味。

##### 早期：让计算机进入普通人的生活，也进入人的文化经验

从 1977 年 Apple II 的集成键盘与机箱，到 1984 年 Macintosh 对图形界面和鼠标操作的重视，很容易看到的是苹果在致力于降低使用计算机的门槛。这里包含沃兹尼亚克和其他团队成员的工作，图形交互也有苹果之外的研究来源，但我们关注的是苹果怎样把技术组织成面向使用者的产品。（详见 [计算机历史博物馆对早期苹果的梳理](https://computerhistory.org/blog/steve-jobs/)）

“走向普通人”并不等于替人包办与决定一切。在 [1977 年《纽约客》的访谈](https://book.stevejobsarchive.com/)中，乔布斯特别看重使用者借电脑学习编程、理解计算机的过程。在这里，我们已经留下一个值得长期思考的问题：好工具是应当让人不必理解它就能使用，还是帮助人理解它、进而有能力改变它？两种追求的确都从关心人出发，却未必指向同一种设计。

乔布斯本人则在 [2005 年斯坦福演讲](https://news.stanford.edu/stories/2005/06/youve-got-find-love-jobs-says)中回忆，自己在里德学院旁听书法课时接触的字体与字距知识，后来影响了 Macintosh 的字体设计。这是他对自身经历的回顾，可以帮助我们理解他为什么把人的感受带入计算机设计；它并不能证明字体和图形界面的全部历史都由他一人开启。

你可以试着站在那个阶段来看待这个问题：如果计算机要成为普通人写作、阅读和表达的工具，那么文字呈现的品质就属于计算机应当关心的事。用户未必会提前提出“请为我提供比例字体”，但这不意味着他们无法感受到更合适的文字关系。创造者可以提出用户尚未说出的可能性，但一切仍要等待用户体验、真实使用与市场结果的检验。

##### 离开苹果之后：技术与审美上的坚持，需要面对采用它们的条件

1985 年，在被董事会投票踢出管理层后，乔布斯与老朋友创办 NeXT。其技术先进但价格高昂，因而没有获得相应的市场成功。公司随后结束硬件业务，转向软件与跨平台合作。其系统技术后来又成为 Mac OS X 的基础。（详见 [基于 NeXT 档案的历史研究](https://computerhistory.org/blog/next-steve-jobs-dot-com-ipo-that-never-happened/)）

这个例子同时印证了两个判断：一项技术可以有长远价值，而承载它的某一代商品仍可能不适合当时的市场。学校或企业是否买得起，已有软件能否使用，迁移是否值得，都属于产品问题。不能把每一次不被采用都解释成用户缺少眼光，也不能因为商业受挫，就断言其中的技术探索毫无意义。

同一时期，乔布斯参与经营的 Pixar 在 1995 年推出《玩具总动员》，其成品依赖计算机技术，也依赖动画师与讲故事的人。从这个案例可以作很简单的思考：观众走进电影院时，并不需要先理解渲染系统。在电影领域，观众购买的不是技术，而是体验，而技术恰恰要经过有技术的叙事与创作才成为观众的经历。这并不是乔布斯某一刻突然“顿悟”的故事，而是在现在看来反而有些显而易见的一件事：讨论产品时，不能只盯着技术的先进程度。（详见 [计算机历史博物馆的相关记录](https://computerhistory.org/blog/steve-jobs/)）

##### 重返苹果：让取舍进入组织，也让合作成为产品的一部分

1997 年乔布斯重返苹果。到 [1998 年的 Macworld 演讲](https://book.stevejobsarchive.com/)中，他用面向消费者 / 专业用户、台式 / 便携的四类产品解释聚焦策略，并把它与团队配置、更新速度联系起来。这里的少，涉及公司怎样分配有限的人和时间。。这与“界面上少放几个按钮”有很大区别。要把一个产品做好，往往需要停止其他同样有吸引力的项目，让设计、工程和支持能够持续照顾少数明确的任务。删掉一个选项很容易，接住因此失去选项的人、承担放弃业务的后果，才是取舍的重量。

同样值得留意的是，苹果与微软在 1997 年达成[合作](https://news.microsoft.com/source/1997/08/06/microsoft-and-apple-affirm-commitment-to-build-next-generation-software-for-macintosh/)，内容包括继续开发 Mac 版 Office、专利交叉授权以及微软投资苹果等。对需要 Office 的 Mac 用户来说，竞争对手愿意继续提供软件，就是购买和使用这台电脑的现实条件。

如果把苹果的价值理解成“必须让微软输”，就很难解释这次合作；如果把重点放在“让选择 Mac 的人有可持续的使用体验”，它就容易理解得多。根据这些决策，我们可以把这一阶段的变化理解为：在坚持体验判断的同时，更清楚地处理资源、合作与生存条件。这个解释有事实依据，但不应被夸大成对他全部心理活动的定论。

##### iPod 到 iPhone：保留追求，修正实现它的边界

2002 年，苹果已为 Windows 用户提供[搭配 MUSICMATCH Jukebox 的 iPod](https://www.apple.com/newsroom/2002/07/17Apple-Unveils-New-iPods/)；2003 年 10 月，又推出 [Windows 版 iTunes](https://www.apple.com/newsroom/2003/10/16Apple-Launches-iTunes-for-Windows/)，把购歌、管理与 iPod 同步进一步整合起来。这有一个很显见的场景：对一个使用 Windows 而只想方便地听歌的人来说，为了一个播放器而去买一台 Mac 是一道很高的门槛。把体验整合延伸到竞争对手的平台上，并不是放弃独占，而恰恰是这样的策略才能扩大自己的市场。用户价值与商业利益在这里同时成立：整合并不是在强制每一个环节，用户都要购买自家品牌的产品。

再来看看 iPhone 不断演进的应用生态：2007 年 6 月，苹果对第三方开发者提供的是[通过 Safari 运行 Web 应用的方案](https://www.apple.com/newsroom/2007/06/11iPhone-to-Support-Third-Party-Web-2-0-Applications/)；2008 年 3 月发布[原生应用 SDK 测试版](https://www.apple.com/newsroom/2008/03/06Apple-Announces-iPhone-2-0-Software-Beta/)，同年 7 月推出 [App Store](https://www.apple.com/newsroom/2018/07/app-store-turns-10/)。我们今天熟悉的应用生态，并不是一蹴而就的。这些变化也至少生动的说明：最初的方案可以被调整，而调整不一定意味着失去了原则。苹果进一步开放第三方创造，同时通过商店分发组织这种开放。它扩大手机能做的事情，也把“由谁决定哪些应用能够到达用户”变成了产品的一部分。

沿着这条线看，乔布斯的产品判断中有连续也有变化：让技术成为人能够使用、感受和表达的东西；而承载这个追求的范围，则从一台机器，一步一步扩展到组织、合作伙伴、内容和开发者。**产品哲学有力量的地方，在于能帮助我们解释何时坚持、何时修改，以及凭什么作出这样的决定。** 任何一个固定的模式，都无以代替你的判断。

#### 为什么永远无法在产品中找到产品的答案？

这里的“无法”可以理解为：只观察一个产品已经呈现出来的形态，我们永远无法充分解释它为什么应该如此，更无法直接推出下一个产品应该怎样做。产品内部能提供线索，判断线索的标准还需要到人的生活与外部条件中寻找。

##### 先看一项设计在什么情况下成立，再看它长什么样

2007 年的[初代 iPhone](https://www.apple.com/newsroom/2007/01/09Apple-Reinvents-the-Phone-with-iPhone/)以大尺寸多点触控屏幕组织电话、音乐和互联网功能。屏幕可以随任务改变控件，这为浏览网页、看照片等场景提供了不同于固定实体键盘的空间。如果我们据此总结出“实体按键越少越先进”的印象规律，放到需要盲操作、戴手套或频繁输入的场景里，这就很明显的并不是一种泛用的产品哲学。

按钮数量只是结果：任务是什么，身体怎样操作，错误的代价有多大，才是作出判断的依据。你可以从 iPhone 学习重新安排交互空间，却不能把每一块触摸屏都当作进步的证明。更进一步来讲，用户的原话也需要放回生活中解释。“我想要更多功能”可能意味着他一直缺少一个关键能力；“我想要更简单”也可能意味着现有规则难以理解。设计者需要追问具体经历，观察用户怎样绕过困难，再提出方案。用户没有说出解决办法，不代表困难不存在；设计者想到了办法，也同样并不代表他已经理解了用户。

##### 为什么微软、谷歌不能只模仿苹果的形式就得到同一种体验？

这里讨论的是特定时期的软硬件、内容与服务由谁协调，以及这对体验一致性有什么影响。Windows 是微软的产品，Android 也只是谷歌参与的一个平台，我们并不意在将某个环节、某个时期的表现扩大成对一家公司的宣判。

苹果在 iPod 与 iTunes 上，把设备、管理软件与商店的关键决策集中起来。微软在 2004 年推广的 [PlaysForSure](https://news.microsoft.com/source/2004/10/12/microsoft-and-partners-announce-new-era-of-digital-devices-enabling-consumers-to-take-entertainment-throughout-the-home-and-on-the-go/)，则通过标识与测试帮助消费者选择兼容的设备和在线商店，参与者包括多家硬件厂商与内容服务商。微软同样在努力减少兼容问题，只是它组织合作的方式不同。

据此可以作出一个有限的推论：在参与方较少、决策较集中的范围内，统一同步规则和操作流程的协调成本通常更低；当设备、商店和软件分别由不同公司经营时，一个改动就可能需要更多协商。后者也能提供更多厂商与服务选择。这是两种组织方式的取舍，不能仅凭这点就解释整个市场竞争的结果。

谷歌在 2007 年公布 [Android 与开放手机联盟](https://googleblog.blogspot.com/2007/11/wheres-my-gphone.html)时，明确将目标放在支持众多手机的共同平台上。到 2017 年，Android 团队推出 [Project Treble](https://android-developers.googleblog.com/2017/05/here-comes-treble-modular-base-for.html)，尝试分离系统框架与芯片厂商相关实现，降低设备升级的工作量。这个工程问题本身，就呈现了多方协作需要处理的复杂性。

我们可以把这些案例中的结构性差异放在一起看：

| 组织体验的方式 | 它比较容易支持什么 | 需要面对什么代价 |
| --- | --- | --- |
| 在较少的自有产品中统一关键决策 | 统一默认行为，集中排查问题，协调完整流程 | 用户的组合选择可能减少，更依赖同一个提供者 |
| 让多家厂商、设备与服务共同参与 | 覆盖不同需求，允许多种产品组合与经营方式 | 一致性、兼容与更新需要跨组织协调 |

企业也会跨越这些边界：微软在 2006 年推出整合设备、软件与音乐服务的 [Zune](https://news.microsoft.com/source/2006/09/14/microsofts-zune-delivers-connected-music-and-entertainment-experience/)；谷歌在 2016 年推出 [Pixel 手机](https://blog.google/products-and-platforms/devices/pixel/introducing-pixel-our-new-phone-made-google/)时也强调将软硬件设计结合起来。因此，“微软永远不懂整合”、“谷歌只会做技术”这类片面的口号都无法解释已经发生的事情。真正值得继续研究的是，在明确的用户、价格和任务下，哪一种组织方式产生了更好的结果？这种结果来自哪些机制，有没有其他解释？换一个约束，原本的优势会不会成为负担？

##### 再往外走一步，你会发现，“好用”本身也包含价值选择

让用户更快完成任务通常是值得追求与优化的目标。但如果一种设计让用户更快冲动购买，却更难退订；让使用更便利，却把迁移成本留到几年以后，我们还需要问：谁得到了什么，谁承担了什么？报表里的一次购买、一项满意度和一段使用时长，通常只能回答其中一部分问题。这也解释了：为什么很多看起来很专业的产品讨论仍然可能是庸俗的。

这里的“庸俗”指一种**过早停止追问的习惯**：接受现成的评价尺度，然后熟练地替它补充理由。

- 把“参数更高”直接写成“产品更好”，省略参数与实际任务之间的关系。
- 把“很多人买”直接写成“所有选择都正确”，省略价格、渠道、替代方案和不同人的处境。
- 把“我喜欢”扩大为“用户需要”，省略与自己不一样的人；把“用户说了”当作结论，又省略对具体困难的理解。
- 把“像苹果”“有高级感”“形成闭环”当成解释，省略这些形式为什么在这个场景里成立。
- 把自己的消费选择变成优越感，用“没有审美”或“不会用”结束对他人困难的讨论。

这些捷径容易被反复使用，因为数字好比较，标签好传播，模仿也容易获得确定感。相比之下，说明一个人的处境、承认自己的判断有条件，是需要很多很多耐心的。我们自己也会采用这些捷径，因此这段讨论其实首先是一种自查。

你是否记得 term1 的 task1 中，我们希望你尝试容纳创作者独特的想法？现在，我们还可以多走一步：同时容纳使用者、维护者和被排除在外的人的处境。产品哲学的深度，也体现在它能否解释这些人为什么有理由不同意你。

#### 为什么我们只能对产品哲学做一种滞后的思考？

当一个产品已经成功，我们再讲它的历史，很多选择都会显得理所当然：书法课通向 Macintosh，音乐播放器通向 iPhone，坚持终于得到回报。历史实际发生时，人们却不知道自己站在哪一段故事里，也不知道哪些尝试最终会留下来。

乔布斯本人也在[斯坦福演讲](https://news.stanford.edu/stories/2005/06/youve-got-find-love-jobs-says)中谈到，自己是回头看时，才把早年的书法学习与后来的设计工作联系起来。这仅是一种审视经验的方式，并不是“只凭直觉就一定成功”的创业鸡汤。

##### 证据本身的局限

发布时可以展示功能，却无法当场展示几年后的使用习惯、维护成本和退出困难。更何况，我们研究的是会回应产品的人：新的能力会改变他们的预期，新的预期又会改变产品应当解决的问题。

2001 年的 iPod 通过电脑管理与同步音乐。到了 2011 年，苹果公布 [iCloud](https://www.apple.com/newsroom/2011/06/06Apple-Introduces-iCloud/)，重点之一是让内容在多台设备间自动、无线地保持更新，减少用户手动维护的麻烦。

这里可以看到，先前帮助人处理复杂性的方案，在新的设备组合中也可能带来新的麻烦。保存某一代的具体流程，未必能够继续保存当初追求的便利。思考产品，需要追踪目标与条件的关系，而不能只保护过去成功过的做法。

再联系他早年对学习编程的重视，两个阶段公开表达的重心也有差别：前者鼓励人探索工具，后者强调工具自动完成事务。它们可以并存，但我们仍可以追问，自动化在什么时候释放了人的精力，在什么时候又削弱了人的理解和掌控？“为了用户好”需要解释的内容，会随着产品介入生活的深度而增加。

##### 对成功故事的偏爱

站在今天的我们当然知道 NeXT 的技术后来会进入苹果，但这容易把早期挫折当成一条注定通向成功的路。没有走到最后的那些人与公司也可能同样执着、勤奋、重视设计，只阅读胜利者的故事，会把一些普遍存在的特征误认成成功的充分原因。同样，iPhone 的后续成功也不能倒过来证明 2007 年的每一个决定都正确。Web 应用到原生 SDK 的变化，就已经提醒我们要把最初的判断、后来的调整和最终看到的结果分开举证与说明。愿景、实施能力、合作、市场条件和时机都可能参与结果，不能把它们全部归给一个名人或一种思想。

##### 我们仍然能够在行动之前思考

无法预先知道全部后果并不等于无法比较方案、指出风险或检验关键假设。我们能够也应当根据自己的知性提出有根据、可修改的判断，只是不能把它想象成历史已经替我们作出的保证。

例如，你准备把校园活动报名从复杂表单改成“一键报名”。行动前就可以说明：希望降低哪类人的负担；哪些信息可以后补，哪些必须提前确认；怎样检查减少步骤后有没有增加误报名；出现什么结果就需要调整。上线后，再把实际经历与原来的判断放在一起看。这个过程中，产品哲学既指导行动，也接受行动的检验。

因此，阅读这段思考时，我们应当给自己保留三个问题：

- **站在当时：** 已经知道什么，还有什么不知道？当时真正可选的方案有哪些？
- **看向后来：** 哪些后果得到了证实，哪些问题是后来才出现的？谁的经历没有进入成功叙事？
- **回到自己：** 我赞同的是他的价值判断，还是只喜欢结果？什么证据会使我改变看法？

产品把一种关于生活的主张变成可被使用、依赖、拒绝和批评的现实。它的哲学就在这些选择及其后果里。你可以欣赏乔布斯，也可以反对他；我们更希望你逐渐能够说清楚自己的理由，并愿意让理由接受生活的检查。

## 作业

参考 [term1 的 task1](../term1/task1.md)，从身边任选一个你愿意认真观察的品牌或产品，完成一篇**博客形式的产品导向思考**。可以是软件、手机、文具、家电、便利店、食堂窗口、校园服务，也可以是不在这些例子中的对象。如果选择品牌，请落到它的一项具体产品或服务经历上。

从你真实接触到的事情开始：一次顺畅的操作，一次让人恼火的等待，一个你用了很久却最近才注意到的细节。对象很普通也没关系，你愿意把一个问题想清楚，比列举很多著名品牌更重要。

文章可以沿用“感想—分析—展望”的线索，自拟标题并自由组织。下面的问题帮助你往深处走，不要求逐项写成问答：

1. **从自身角度出发的感想：我经历了什么？**
    - 写明对象、接触时间与具体场景；涉及软件时，尽量记录版本、设备等会影响判断的条件。
    - 当时想完成什么，实际怎样做，在哪里感到舒服、困惑或受阻？至少讲清楚一次具体经历。
    - 你最初的好恶来自使用本身，还是价格、宣传、他人评价与品牌印象？它们可以同时存在，试着分辨。
2. **从产品角度出发的分析：它为什么作出这些选择？**
    - 选一个最值得讨论的决定，例如默认设置、定价、菜单、功能删减、会员规则、包装或售后。
    - 它优先照顾了谁的什么需求？放弃了什么？使用者、付费者、经营者和维护者的利益是否一致？
    - 找一个真实的替代办法作比较，可以是同类产品，也可以是人工、纸笔或“不使用它”。尽量保持任务与条件相近，说明各自的收益与代价。
    - 结合实际细节与可核查材料，解释背后的价值取向；把自己的推测写成推测，不要替品牌编造动机。
3. **从未来角度出发的展望：我是否还赞同最初的判断？**
    - 提出一个对自己结论有挑战的反例：换一种用户、预算、环境或使用阶段，原本的优点还成立吗？
    - 如果由你负责，最想坚持什么，愿意调整什么？改动会增加哪些成本，又可能让谁失去便利？
    - 说明还需要什么观察或验证，才能判断这个建议是否有效。允许得出暂不改动的结论，但要解释理由。

如果一时不知道怎样下笔，可以从这样的小问题开始：“我一直觉得食堂窗口提供越多套餐越好，为什么午间赶课时又希望它少一点？”接着比较赶时间与慢慢挑选两种处境，再考虑窗口的备餐、选择与排队。这里只提供一个观察入口，具体判断应来自你自己的经历。

> [!IMPORTANT]
> 你不需要赞同本文，也不需要分析苹果。能够用细节与证据指出这篇文章的局限（我们确实预留了一些关键的思考与判断没有写出），同样是有价值的产品思考。
>
> 尽量在文章里留下三种声音：当时的你、现在重新思考的你，以及一个可能不同意你的人。不要让最后一个人只是为了被你轻松反驳而出现。

引用产品公告、历史资料、他人的感悟或研究时，应当标明出处或给出链接，并附上自己的分析。亲身经历、可核查事实、品牌主张与个人解释应当能被读者区分。

字数适中，能够把一个关键问题说清楚即可，不要堆砌术语、名言与案例。我们会关注你的观察是否具体、推理是否解释取舍、是否认真面对不同处境、以及你能否在交流中说明自己为什么这样想。
