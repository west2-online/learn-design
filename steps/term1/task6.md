## 学习

### 资产库的构成

> [!TIP]
> 资产库的难点从来不是“存起来”，而是“找得到、敢用、用得明白”
> 收集不是终点，能够快速找到、合法使用、稳定复用才是资产库的价值

1. 按资产类别划分
    - 字体 / 图标 / 插画
    - 画笔 / 纹理 / 材质
    - 真实摄影 / 音视频
    - 数字化创作 / 3D 资产
    - UI 组件 / Design Token / 组件库
    - etc.
2. 按资产库用途划分
    - 参考库：保存网页、案例、文章与灵感，帮助检索和回溯，不默认拥有其中内容的使用权
    - 通用资产库：保存已确认来源与授权、能够跨项目复用的字体、图标、图片、音视频与源文件
    - 项目资产库：只保存当前项目实际使用的资产、修改记录与交付版本，避免直接依赖个人资产库
    - 设计系统：管理组件、样式、Design Token、使用规范及其在设计稿与代码中的对应关系
3. 按授权范围划分
    - 原创：明确作者、参与者及团队内部的使用范围
    - 公共领域 / CC0：确认授权声明后使用，可参考 [Creative Commons](https://creativecommons.org/) 的授权说明
    - 允许使用：记录署名、商用、修改、再分发等具体条件
    - 限制使用：仅在符合授权的项目与场景中使用
    - 仅供参考：不可直接进入最终交付
    - AI 生成：记录模型、生成时间、参考素材与平台条款，人工检查潜在侵权风险
4. etc.

### 资产生命周期

1. Collect：从浏览器、平台收藏夹、聊天记录和本地文件夹汇总到 Inbox，不在收集时过度分类
2. Review：检查来源、授权、质量和重复项；信息不完整的资产留在隔离区，不进入可用库
3. Normalize：统一文件名、格式、色彩空间与目录结构，保留未经破坏性处理的 Original
4. Register：分配稳定 ID，补齐作者、来源、授权凭证、标签、预览、适用场景与维护者
5. Approve：由维护者确认后发布到 Approved 区域；团队成员默认只从已批准版本中取用
6. Use：在项目中复制或引用资产，并记录使用项目、修改内容、责任人及对应版本
7. Update：新版本通过评审后发布，说明变化、影响范围、迁移方式与旧版本停止使用的时间
8. Archive：定期检查失效链接、到期授权、重复资产和废弃版本；归档与删除应可追溯，并遵循备份策略
9. 工作流状态至少区分 `Inbox / Reviewing / Approved / Deprecated / Archived`，状态变化应有明确负责人

### 技术选型

> [!TIP]
> 选型前先确认资产类型、数量、协作方式、权限要求、备份责任与可接受的维护成本
> 不便自托管时，可以用能够导出的替代品，不因工具不同改变元数据与授权要求

1. 参考链接库
    - 推荐主线：[linkding](https://github.com/sissbruecker/linkding)，通过浏览器扩展、标签和批量导入，将不同浏览器中的收藏集中到可自托管、可导出的参考库
    - 需要网页快照、批注与更完整协作时，可选择 [Linkwarden](https://github.com/linkwarden/linkwarden)
2. 个人文件型资产库
    - 推荐主线：[TagSpaces](https://docs.tagspaces.org/)，直接管理普通文件夹，并使用可随文件迁移的标签、描述、预览与 JSON sidecar 元数据
    - 重视视觉化收集效率、相似图片查找与开箱即用体验时，可选择 [Eagle](https://www.eagle.cool/)，但需额外关注商业软件授权、团队协作方式与数据导出能力
3. 项目资产与版本管理
    - Markdown / JSON / HTML / CSS / SVG 等文本资产直接使用 Git 管理
    - PSD / AI / Blender / 音视频等二进制大文件可使用 [Git LFS](https://git-lfs.com/)，但需提前确认远端存储、流量配额与历史迁移成本
4. UI 组件与 Design Token
    - 设计侧使用 [Figma Library](https://help.figma.com/hc/en-us/articles/360025508373-Publish-a-library) / [Penpot Library](https://help.penpot.app/user-guide/design-systems/libraries/) 的组件、变量与 Library 维持唯一来源、状态和变体
    - 实现侧可使用 [Storybook](https://storybook.js.org/) 隔离展示组件状态、补充使用文档并参与验收
5. 团队 DAM
    - 当普通文件夹已无法满足多人检索、审批、权限、版本与审计需求时，再评估 [ResourceSpace](https://www.resourcespace.com/) 等 Digital Asset Management 系统
    - 自托管不是默认加分项，需要同时说明部署、对象存储、备份、更新、安全与离任交接由谁负责
6. 推荐学习顺序
    - 先使用 `linkding + TagSpaces + Git / Git LFS + Figma / Penpot` 跑通完整流程
    - 实际需要多人审批、权限隔离和大量资产分发需求后，再尝试搭建团队 DAM

### 统一文件结构与可复用性

1. 统一文件结构
    - 原始文件 / 可编辑源文件 / 导出文件 / 预览文件分开保存
    - 使用能够被其他人理解和检索的文件名
    - 保留必要版本，及时清理重复、失效与来源不明的资产
    - 个人资产库与项目资产库分开管理，项目资产通过公共空间同步
2. 记录资产信息
    - 原始来源、作者、获取时间与授权凭证
    - 内容标签、风格标签与适用场景
    - 文件格式、色彩空间、尺寸与对应软件版本
    - 曾用于哪些项目、经过哪些修改、由谁维护
3. 提升可复用性
    - 为高频资产提供预览、使用说明与可编辑版本
    - UI 组件明确状态、变体、响应式行为与使用边界
    - 字体、组件、图标等发生更新时，记录影响范围并通知项目成员
4. etc.

## 作业

> [!TIP]
> 资产库的维护水平难以通过一次提交完全验证，因此本任务拆成两部分：
> 提交物考察你“把资产库建起来”的能力，面试中的现场小选题考察你“把资产库用起来”的熟练度
> 两部分会结合前面任务的完成度一起考核

1. 建设个人资产库：
    - 使用 `linkding + TagSpaces + Git / Git LFS + Figma / Penpot` 跑通完整流程，不便自托管的部分可用能导出的替代品代替，但需说明理由
    - 将 task1 到 task5 过程中产生的资产收编入库，至少包括：
        - 你在各任务中收集的参考链接与文章
        - 任务中使用的图床图片、SVG、字体与其他素材
        - task2 与 task4 的 Figma 组件、Styles 与 Token
        - task5 的 Prompt 记录、Skill 与生成结果
    - 建立参考库 / 通用资产库 / 项目资产库 / 设计系统的用途划分，并为每类资产补充来源、作者、授权凭证与必要标签
    - 统一文件结构：原始文件 / 可编辑源文件 / 导出文件 / 预览文件分开保存，使用他人能够理解和检索的文件名
    - 建立 `Inbox / Reviewing / Approved / Deprecated / Archived` 的状态区分，并记录每次状态变化
    - 记录资产信息：来源、获取时间、授权、格式、色彩空间、尺寸、使用项目与维护者
2. 记录建设过程与复盘：
    - 说明你的目录结构、命名规则、标签体系与授权分类是如何设计的，取舍是什么
    - 记录建设中遇到的问题：失效链接、来源不明的资产、重复文件、超限文件等是如何处理的
    - 说明同步与备份策略，并明确区分“同步”与“备份”
    - 复盘：经过本次收编，你在前面任务中有哪些收集习惯可以改进
3. 现场小选题考核：
    - 面试时从以下题库中自选 2~3 条，每条需在 10~15 分钟内全程在面试中共享屏幕完成，完全允许使用自己的资产库与工作流
    - [题库](docs\task6.md)将持续扩充，考核负责人也可以基于题库临场出新的相同难度的题目；需要样本包的题目则需要负责人提前准备
    - 评分不以最终目录是否“好看”为标准，而以决策是否有依据、能否口述理由、能否被他人接手为标准；资产库没有唯一正确答案

4. 提交内容：
    - README 需涵盖目录结构说明、处理记录与复盘内容、说明环境要求、工具选型与替代方案、目录结构、命名与标签规则、授权分类、同步与备份策略，以及其他人如何接手维护
    - 提交资产库的结构展示（目录树截图或文件树说明）与代表性处理案例（如某个资产的完整生命周期记录）
